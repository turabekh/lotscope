# 19. Web-push notifications

Date: 2026-06-28

## Status

Accepted

## Context

ADR-0018 delivered email digests; the remaining half of PRD §5.16 is **push** — a real-time-ish nudge when a watched lot changes, without the user opening the app or email. Web Push needs a server VAPID keypair, payload encryption, a frontend service worker, and per-device subscription storage.

## Decision

**Standards-based Web Push (VAPID), dormant without keys, as a nudge that does not consume alerts.**

- **Sending:** `pywebpush` (handles the Web Push encryption + VAPID JWT) called from a thread in the async worker. `get_push_sender(settings)` returns `None` when `VAPID_PRIVATE_KEY` is unset, so the cron logs-and-skips. Keys are base64url raw P-256 (43-char private / 87-char public `applicationServerKey`), generated by `make vapid-keys`.
- **Subscriptions:** a `push_subscription` table (per user, unique by `endpoint`, storing `p256dh`/`auth`). `POST /push/subscribe` upserts by endpoint; `POST /push/unsubscribe` deletes; `GET /push/vapid-public-key` returns the public key (or `null` when unconfigured) for the browser's `applicationServerKey`.
- **Frontend:** a `public/sw.js` service worker shows the notification and opens `/watchlist` on click; an account toggle requests permission, subscribes via `PushManager`, and posts the subscription. Unsupported browsers show "Not supported"; a blocked permission surfaces an error.
- **Trigger:** a **daily** ARQ cron (`send_push_alerts`, 12:00) pushes to every subscribed user who currently has watchlist alerts, a one-line "N lots changed" nudge. Dead endpoints (HTTP 404/410) are pruned on send.
- **Push does not acknowledge.** Unlike the email digest, sending a push does **not** re-snapshot the alerts. Push is a nudge; the alert clears only via the email digest (its cadence) or in-app "Mark seen".

## Consequences

- **Push and email are independent channels** over the same alert computation. Because push doesn't acknowledge, a user with push but no email gets a daily nudge until they act in-app — acceptable for an opt-in browser notification, and it avoids the cross-channel "first sender consumes the alert" ordering problem.
- **Per-device, not per-account:** subscriptions are browser/device-scoped; a user enables push on each device. Expired subscriptions self-prune.
- **Dormant + safe:** no keys ⇒ no sends, no errors; the toggle still renders and reports unavailability.
- VAPID keys are secrets (the private key signs pushes) — env-only, never committed.
- **Deferred:** notification preferences/quiet-hours, per-change (vs daily) push, click-through deep links to the specific parcel, and richer notification actions.
