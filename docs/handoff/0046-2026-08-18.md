## 4. The findings that matter most

**Scheduled jobs never received the timeouts they declare.** arq resolves a cron job's timeout from the `cron()` entry, not the `func()` registration. All six long-running jobs carried theirs on the `func()` side only, so each ran under the 30-minute worker default. `cron(recompute_verdicts, weekday="sun")` is among them — an ~11.5h job under a 30-minute cap, cancelled every Sunday since it was scheduled. **This is a large part of why v9 and v10 were never swept.** Fixed in #155 with a drift guard; #157 added the cron run history, because nothing had ever recorded how long a scheduled job takes, which is why it stayed invisible.

Found because OPA failed at **04:30:01**, thirty minutes and one second after its 04:00 cron, with the sweep saturating the box. One cancelled dataset ends the whole nightly ingest — `ingest_market` re-raises `CancelledError` rather than collecting it — so only OPA was attempted. **That failure was caused by running the sweep.** Data is two days stale, not damaged.

**A gated scoring change shipped early, through data rather than code.** `is_absentee` is unconditional and the batch never touched it; the mailing backfill went in on 08-16 as a "data operation" and the nightly distress cron scored it that night. All 30,119 absentee-vacant parcels already carried their +10 before the sweep; only 5 parcels rose at all. **A version gate on a derived score only holds if its inputs are gated too.**

**The predicted risk movement was one of three paths.** `verify` does not merely reword the delinquency flag — it halves the weight of any `high` delinquency, and `verify` is reached by two populations the ADR's delta never counted. Decomposition in the ledger; the open judgement is item 1 above.

## 5. Things that will bite the next session

**Never deploy while a sweep is running.** `compose up -d` recreates the worker and kills detached shards.

**Deploy without GitHub Actions:**
```
ssh -i ~/.ssh/lotscope_deploy turaboy@34.148.129.129 \
  "cd ~/lotscope && BACKUP_BUCKET=gs://lotscope-501014-db-backups bash deploy.sh"
```
Identical to what the workflow invokes, so backup, migrations and drift guard all still apply. `BACKUP_BUCKET` is not in the VM environment and `deploy.sh` refuses to migrate without it — it fails safe.

**Four shards saturate the box.** 0.0% idle, 0.0% iowait, ~19–23 parcels/s, **~8 hours** for a full Philadelphia verdict sweep. More shards cannot help. The "~4h" projection was wrong by half; the older ~11.7h estimate was closer. Distress sweeps in **~4 minutes** — it is cheap, verdicts are not.

**A version-mixed baseline will mislead you.** `pre_v11_*` spans v8/v9/v10, so comparing v11 against it conflates code change with weeks of data change. It did this twice: it inflated the ledger's verify-cohort estimate to ~6,169 when the direct count is **3,867**, and it produced 12,123 phantom "risk rises" in the gate, all of them v9-baseline rows. **Scope comparisons to the immediately prior version.**

**A guard that cannot fail is worse than none.** Four written this session were wrong on the first attempt: the cron comparison never intersected because `cron()` prefixes `"cron:"`; a health-board filter compared upstream table names against short registry keys and would have emptied the board entirely; and two `verify-v11` checks failed for the wrong reason. **Always verify a new guard fails with its fix reverted, and that the populations it compares are non-empty.**

**Prod latency from a dev machine is ~250ms RTT.** A 0.76s API response is three round-trips over ~16ms of server time. Not degradation.

**`scripts/pull-prod-db.sh --confirm`** refreshes local from production instead of re-running an 8-hour sweep. It destroys the local database, and the copy carries **real owner PII and real user accounts** — local seed logins stop working, since production's user table replaces them. §13 applies to the local copy.
