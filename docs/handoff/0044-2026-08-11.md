## 3. Findings that changed decisions (do not re-derive these)

**The overlay footprint is six sections, not three.** `98cadfa` corrected the RSA-5 scalar arguing the damage was "confined to three overlays". There are six, and the two largest — `/EDO` 13,530 and `/SIX` 12,042 — were never counted. **54,376 of 112,916 flip-band parcels (48%)** sit where 1,440 is correct, making the bare scalar roughly a one-for-one trade of false negatives for *false positives*. That commit was reverted (`4122af1`) and the fix moved to v9.

**The six overlays preserve the small-lot exception verbatim.** Same trigger, floor and provisos. So the blanket suppression that fired on any of 193 overlays was withholding a correct answer — a live defect, not a modelling gap.

**RM-1 does not transfer clean from RSA-5.** `/CTR` (§14-502(4)(c)(.2)) sets a different trigger (1,600), floor (800), and a hard **two-lot cap** that `SmallLotProvision` cannot express. Only the base provision is modelled.

**The adjacency predicate was checked and is faithful.** The code says only *"lots adjacent to the lot to be divided"* — no block-face qualifier. All five RSA-5 constants match verbatim. **Recorded so it is not re-litigated.**

**An error in the audit, corrected in ADR-0080.** Its §4/§6 read *"19,435 of them clear the 1,920 trigger"*. 19,435 is the **≥1,600** count; the ≥1,920 figure is **10,946** — two columns of one query transposed in prose. Conclusion unaffected, headline wrong by 1.8×.

## 4. The benchmark, and the two deploy defects it surfaced

**The hazard:** verdict reads recompute lazily on version mismatch, so merging v9 put a full `compute_verdict` on the request path of every parcel view — making the overlay join a user-facing cost, not a batch-job one.

| | overlay lookup | `assess_parcel` | full phl recompute |
|---|---|---|---|
| v8 baseline | — | — | 10.38 h |
| v9, live `ST_Intersects` | 27.1 ms | 30.6 ms | 15.30 h |
| **v9, materialized** | **1.5 ms** | **2.15 ms** | **11.70 h** |

**Both GiST indexes already existed** — this was never a missing-index problem; it is the exact-intersection test against 193 polygons paid per parcel. Materialization: **1,487,536 rows in 57 s**, one spatial pass. v9's own overhead **+4.92 h → +1.13 h**.

*Correcting an earlier claim of mine:* I had cited a 120 s timeout as evidence the request path was at risk. That was a **bulk 3,000-parcel** join. Per-request cost was always ~30 ms. The mitigation is still right; the recompute was the real problem.

### Two defects found by reading the deploy path before running it

Both were introduced by this session's own performance work. **Neither would have failed a test or a CI gate.**

1. **`scripts/deploy.sh` seeded and started the app with no membership step.** Under v9 that writes RSA-5 = 960 and opens traffic against an empty `parcel_overlay` — which does not error, it resolves every parcel to its base standard. That is 960 citywide with no overlay applied: the 54,376-parcel false-positive state, in production. The runbook warned about it while the script did not implement it. The refresh now runs between seed and app start and **exits nonzero if any market lands at zero rows**.
2. **The refresh was hardcoded to `phl`.** Switching `get_parcel_overlays` to the materialized table silently emptied **Wilmington's** overlays — 7 polygons, 14,777 memberships, a live market losing a rendered field with no error. Markets are now discovered from `zoning_overlay`.

**Lesson worth carrying:** the dangerous states in this slice are all *silent* — empty membership, wrong market scope, a stale version stamp. None of them throw.

**Value-based, never version-based** — the drift that motivated it held 960 under the *same* `code_version` as 1,440, so a version-keyed check is blind to exactly the error it exists to catch. **It cannot run in production.** It queries `code_provision`, which prod holds intentionally empty, so it reports all six overlay cites absent and exits nonzero there. It is a local/corpus-loaded ops check — **do not wire it into a prod health check.**

## 6. Ledgered follow-ups (also in ADR-0080's "Open at acceptance")

1. **Overlay dimensional classification.** The suppression narrowing is correct but barely bites: on a 3,000-parcel sample of RSA-5 lots above the small-lot trigger, **none** had only modelled overlays. `/NIS` (Narcotics Injection Sites) touches 2,825 of 3,000. Classifying all 193 overlays by whether they bear on dimensional standards is what would actually unlock small-lot analysis. **Highest-value follow-up.**
2. **`[N/A]` overlay codes.** 1,817 of that sample touch overlays whose `code` is the literal string `[N/A]` — an ingest data-quality defect that degrades any code-keyed overlay logic.
3. **`zoning_overlay.last_synced_at` is NULL on all 193 rows.** Materializing membership gave the layer a refresh cadence; the source layer still has no freshness signal.
4. **`/CTR`'s RM-1 variant** needs a lot-count cap the schema cannot express.
5. **RMX-3's front/rear setbacks** — the audit could not resolve 25 ft against Title 14 (table cell blank); needs the Quick Guide page. Seed may be asserting a constraint the code does not impose.
6. **Parser defects filed upstream, unpatched:** Table 14-701-4's dropped `District Name` header row, and four zero-row `#table2` continuations. Both generalise.
7. **Seven `SP-*` districts unaudited** — their standards live in §§14-404…14-409, outside Tables 14-701-1…-4.
