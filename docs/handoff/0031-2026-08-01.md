## 3. The deploy — and the failure it uncovered

### 3.1 First attempt failed: a stale `VM_HOST` secret

Run `30674398315` failed in ~30 seconds:

```
dial tcp ***:22: i/o timeout
```

This is the **second-order half of the 0030 §3.2 IP incident**. When the VM's ephemeral IP was released on 2026-07-28 (`35.231.170.181` → `34.148.129.129`), the owner corrected the Namecheap `A` records and the site returned on the domain. But `deploy.yml` does not use the domain — `appleboy/ssh-action` connects with `host: ${{ secrets.VM_HOST }}`, and that secret holds a **literal IP**. It was last set **2026-07-06**, three weeks before the address changed.

So DNS and the deploy path are two independent copies of the same address. Fixing one said nothing about the other, and **only a deploy exercises the second** — which is why the site looked healthy for three days while deploys were dead.

Evidence gathered before touching anything:

| Check | Result |
|---|---|
| `gh secret list` → `VM_HOST` | last updated 2026-07-06 |
| `nc -z -w 8 35.231.170.181 22` | timeout |
| `nc -z -w 8 34.148.129.129 22` | **open** |
| `default-allow-ssh` | `0.0.0.0/0` tcp:22 — firewall was never the cause |
| `dig +short parcelphl.online` | `34.148.129.129` |

**The failure was clean.** It died at the TCP dial, before `deploy.sh` ran — no backup, no migration, no container restart, no partial state to unwind. A timeout at this step is always safe to retry once the host is corrected.

**Fix:** `VM_HOST` set to `34.148.129.129`, the reserved static address (`lotscope-static`). Chosen over the hostname deliberately — using `parcelphl.online` would survive a future IP change without a secret edit, but it makes every CI deploy depend on Namecheap resolving correctly, adding a second external system to the deploy path. With the address now static, the IP is the smaller dependency.

**Diagnostic order for next time:** a deploy that times out on port 22 → check `gh secret list` timestamps against the date of any known IP change **before** suspecting the firewall.

## 6. Process notes

- **A healthy site does not mean a healthy deploy path.** Three days of green `/api/health` hid a dead `VM_HOST`. Anything that duplicates a value across two systems (DNS and a CI secret) needs both updated together, and only the action itself proves the second one.
- **Trust the terminal event, not the wrapper's exit line.** 0030 told the next session to look for `rc=0`; the log did not write one. The recompute's own final log event was the reliable signal. When a documented check does not match reality, measure the underlying thing rather than concluding failure.
- **Cheap failures are worth distinguishing from expensive ones.** The first deploy failed before doing anything, so the correct response was a one-line fix and an immediate retry — no rollback analysis, no state inspection. Knowing *where* in the sequence a failure landed decided the whole response.
