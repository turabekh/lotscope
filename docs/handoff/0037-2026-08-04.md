### 2.1 The confidence invariant (ADR-0074)

`_confidence()` read two booleans — is lot area known, is lot width known — and returned `high` when both were present. **545,388 of 550,945 Philadelphia parcels (99.0%) satisfied that test**, so `high` was the default state of the city rather than a signal. LR-B004 forbids exactly that. The pilots were already protected: pgh/wlm/hbg carry `provisional` standards which force `low`, so the exposure was Philadelphia alone.

Two design choices were settled by measurement rather than intuition, and both are worth keeping:

- **District *method* was the wrong rule; district *corroboration* is the right one.** The plan assumed `opa_attribute` was the weak source. Across 3,000 sampled parcels holding both a geometry and an OPA code, the spatial lookup and the OPA attribute **agreed on 2,998, disagreed on 2, and never failed to match**. Neither method is weak on its own. What is informative is whether a second source confirms the first — and both values were already loaded, so it costs no extra query.
- **Overlays were excluded deliberately.** 96.4% of sampled parcels intersect an overlay, but **90% of that is `/NIS`**, which restricts safe-injection sites and cannot affect a vacant lot's envelope. A blanket rule would have demoted the city for nothing. See §4.

### 2.2 The checklist was saying something false (#112)

Reported from a screenshot: four identical rows reading *"No zoning standard is loaded for this district"* directly beneath two rows quoting that same standard's 90% lot coverage and 500% FAR.

The condition was **inverted**. `DimensionalContext.district_code` was taken from the standard, so it was non-`None` exactly when a standard *had* loaded — meaning that message was reachable only when a standard existed, while a genuinely absent standard reported "the base district could not be resolved". Both messages were wrong every time they appeared. **46,524 phl parcels (8.4%) carried at least two such rows; 18,388 carried four.**

Separately the panel rendered `item.category`, and nine dimensional checks share `"Zoning & buildability"`, so distinct checks read as one duplicated row. Each check now carries its own label.

**The pre-existing test asserted only `status == "not_evaluated"` and never looked at the text.** That is why a false statement shipped under a green test.

### 2.3 Unregulated is not unknown (ADR-0075) — the most consequential change

`NULL` on a dimensional field meant two incompatible things and everything downstream read it as the second: *the district imposes no such standard*, and *we never captured the value*.

The provenance hid it. `zoning_standard` **and** the so-called "Title 14 corpus" both derive from one document the seed already cites — the [Base Districts Quick Guide, Feb 2026](https://www.phila.gov/media/20260213170558/ZONING-QUICK-GUIDE_feb-2026.pdf). The corpus is 39 rows, one summary per district. Neither is the code text.

Reading the guide's dimensional tables directly shows **three** states:

| districts | guide shows | state |
|---|---|---|
| CMX-3 / 4 / 5 | no height row, no lot-minimum rows; FAR 500–1200% | **unregulated** — bulk governed by FAR + §14-702 bonuses |
| CMX-2 / 2.5 / IRMX / ICMX | no lot-minimum rows; heights stated | **unregulated** (lot minimums) |
| RMX-1 / 2 / 3 | `Min. Lot Width  N/A  N/A  N/A` | **unregulated**, printed explicitly |
| CA-1 / CA-2 | no lot-width row; uses minimum street frontage | **unregulated** (width) |
| I-1 / 2 / 3 | "60 ft. where abutting a Residential or SP-PO district; otherwise no limit" | **conditional** |
| RM-2 / 3 / 4 | row reads "Max. Height / FAR" → 70% / 150% / 350% of lot area | **conditional** |
| CMX-1 | "dimensions are based on the requirements of adjacent residential districts" | **conditional** |

The last three are regulated and irreducible to one figure. Calling them missing data would be as wrong as calling them unregulated — which is why there are two disposition values and not a boolean.

**19 phl districts carry dispositions. Only districts read directly from the guide were given one**; asserting "no standard applies" without that evidence would be worse than the vagueness it replaces.

### 2.4 The program statement (LR-B-010, #114)

The dossier answered the developer's first question with `RM-1: buildable by-right (4 unit); est. …`. It now reads:

> On this 15,592 sq ft CMX-4 lot, multi-family and commercial uses are permitted by right. CMX-4 sets no maximum height; bulk is governed by a 500% floor-area ratio and a 90% lot-coverage limit instead. After the district's required yards, the buildable footprint calculates to about 11,800 sq ft.

with a claim table stating how each figure was established (`verified` / `calculated` / `estimated` / `unavailable` — LR-B-001's taxonomy, reused not reinvented) and a citation carrying the standards version.

**Conditional language is derived from the checklist, not authored separately** — `not_evaluated` rows become "still unevaluated", `potential_issue`/`fail` rows become "flagged for a closer look, the figures above may change". One source of truth, so the prose cannot drift from the checks below it.

## 4. What the data question actually answered

Asked where to source the data behind the unevaluated checks — unit density, parking, utilities, deed restrictions. The answer is not one thing:

- **Unit density, min lot area, min lot width, max height** — Title 14 itself, not a dataset. Our source is the Quick Guide summary. **For a large share of these there is no data to get: the district sets no such standard.** That is what ADR-0075 encodes.
- **Parking & loading** — Chapter 14-800, which the guide does not cover at all ("parking" appears in it only as a §14-702 *bonus*). `min_parking_spaces` is null for every district and **must not be given a disposition** until the chapter is ingested.
- **Deed restrictions** — the pipeline exists and is wired (`DeedDocument` → `DeedRestriction`, OCR + RAG). The corpus holds **2 documents covering 2 parcels** out of 550,945. An acquisition and cost problem, not an engineering one.
- **Utility service** — genuinely external. OpenDataPhilly publishes PWD water service lines, combined sewer service areas, and stormwater billing parcels — but those describe service-line *material* and sewer *catchments*, not whether a vacant lot has a live connection. They would support a narrower claim than the check implies.

**The blocker for both overlays and parking is the same:** Title 14 full text. `codelibrary.amlegal.com` serves it but **403s automated fetches**, so ingestion needs a licensed feed or a manual export — not a scraper.

## 5. Process — what went wrong, what caught things

**A green test suite proved nothing, again.** The false checklist message shipped under a test that asserted only the status enum and never read the text. Every test written this session asserts the user-visible string.

**Alembic autogenerate is dangerous in this repo, not just for `deal`.** Asked for one column, it additionally wanted to create five `staging.*` tables and `raw.raw_record`, drop `uq_app_user_stripe_customer_id`, drop `ix_parcel_correction_status`, drop `repository_listing.external_id`, and alter geometry types on seven tables. Running it would have been destructive. **Always hand-write the migration**; use autogenerate only to discover the DDL.

**Squash-merging a stacked PR's base with `--delete-branch` closes the child.** #110 was auto-closed, could not be retargeted (`Cannot change the base branch of a closed pull request`), and had to be reopened as #112. For stacks: merge the parent *without* `--delete-branch`, retarget the child immediately, then `git rebase --onto main <old-parent-tip>` to replay only the child's commits.

**A deploy that silently does nothing.** `scripts/deploy.sh` ran `alembic` and nothing else, so #111 would have shipped **inert** — column present, every disposition `{}`, dossier unchanged. Reference data reached production only if someone remembered `make seed`. Now the deploy seeds (#113).

**Check your instrument before believing it.** The seed step looked like it only covered phl and hbg. It did not — the local image was two weeks old and predated the pgh and wlm seeders. Rebuilt, all four markets seed. Same lesson as last session's `ps`-not-installed.

**The same defect shape appeared three times.** A confident headline sitting above evidence that undercuts it: "Buildable by-right" above an unsafe-L&I `fail`; a master-plan district reporting "1 by-right unit"; a non-conforming lot reporting "By-right units: 2". Two were caught by tests while writing #114; the first was caught by the owner looking at a screen. **Nobody has swept for this systematically** — see §6.

**Local dev servers were killed twice by the harness**, with zero bytes of output and no stray processes — not a crash. Run `make dev` from your own terminal rather than as an agent background task.
