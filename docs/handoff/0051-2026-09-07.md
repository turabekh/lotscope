## 2. The weekly restore check had never run, and could not have

Two independent fatal bugs, both invisible because each killed the script before it
could record anything. Found only by running it by hand, which is the whole argument for
running it by hand.

**First:** `df -P --output=avail /` is a flag combination `df` refuses.

```
df: options -P and --output are mutually exclusive
scripts/verify-backup.sh: line 54: * 1024 : syntax error: operand expected
scripts/verify-backup.sh: line 55: free_bytes: unbound variable
EXIT=1
```

That is the disk precheck, the script's first real statement. It died there every Sunday,
and because the failure happened before `fail()` was reachable it wrote no `job_run` row —
and a weekly job that writes nothing looks exactly like a weekly job not yet due.

**Second:** with the precheck fixed the restore worked, and then the recording died.

```
==> Restored 588715 parcels from lotscope-nightly-20260906T112900Z.dump (2303007666 bytes)
ERROR:  syntax error at or near ":"
LINE 3: ...backup:restore_check', 'restore_check', 'backup', :'status',...
```

psql expands `:'var'` only in input it lexes itself; a `-c` string goes to the server
verbatim. The success path and the failure path shared that one statement, so neither
could ever have written a row.

Both fixed, plus an ERR trap so an abort that never reaches `fail()` still records the
line that killed it. Then the whole script run against production, start to finish:

```
id           | 413
job_id       | backup:restore_check
label        | restore_check
kind         | backup
status       | success
started_at   | 2026-09-07 00:15:46+00
finished_at  | 2026-09-07 00:33:41.46869+00
duration_ms  | 1075469
result_count | 588715
error        |
```

The disk figures it checked: **53,363,405,824 bytes free** (`df -Pk /` reported
52,112,688 KB) against a database of **24,894,643,223 bytes**, needing twice that —
49.79 GB required, 53.36 GB available, so it proceeded. Free space fell from 50 G to
27 G during the restore and returned to 50 G when the scratch database was dropped
(`SELECT count(*) FROM pg_database WHERE datname = 'lotscope_restore_check'` is 0).

**It takes eighteen minutes, not the five the last handoff estimated.** The 03:30 Sunday
slot is still clear of the 04:00 ingest, but only just — the restore now overlaps the
nightly ingest's first fifteen minutes on the same disk and the same Postgres.

## 5. Playwright in parallel

**The workers do not contend over the fixture parcels.** They contend over `pnpm dev`.

A lot page load pulls ~270 module responses out of the single-threaded Vite dev server
against ~20 API responses. Measured, browsers loading `/lot/phl:99900002` concurrently:

| concurrent browsers | slowest load, dev server | slowest load, built bundle |
|---|---|---|
| 1 | 2,363 ms | 2,346 ms |
| 4 | 9,086 ms | 6,550 ms |
| 8 | 17,074 ms | 10,895 ms |

Against a 10s `expect` timeout, which is why failures went 0 → 1–4 → 22 as workers went
1 → 4 → 8. On an idle box every endpoint the page touches answers in under 0.4 s — the
API is not the bottleneck, and neither is the database.

Fixed by serving `vite build` + `vite preview` (about four seconds of build once, static
files after), with the `/tiles` proxy lifted into a constant that both `server` and
`preview` read. One genuine race went with it: the deals stage dropdown saves on change
and the test called `page.reload()` on the next line, cancelling the PATCH it was about
to assert on — it failed three runs out of three.

| workers | before | after |
|---|---|---|
| 1 | 58/58, 2m06s | 58/58, **1m55s** |
| 2 (CI) | 58/58 1m27s · 58/58 1m34s | 58/58 **1m22s** · 58/58 **1m26s** |
| 4 (local default) | 58/58 1m37s · **57/58** 1m42s · **54/58** 2m30s · **55/58** 2m12s | 58/58 **1m25s** · 58/58 **1m32s** · 58/58 **1m28s** |
| 8 | **36/58** (22 failed) | **48/58** (10 failed) |

**Correction to handoff 0050:** CI runs two workers, and two workers was never red — it
passed before the fix, twice, without retries. The failures start at four, which is the
local default. Eight workers on eight cores still fails ten tests; that is CPU
oversubscription, not a defect, and no configuration anyone runs is that oversubscribed.
