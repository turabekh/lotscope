## The sale-year pivot bug (PR #34)

The one real defect the ingest surfaced. `_wlm_sale_date` pivoted two-digit `SALEYR` on a fixed
constant (`_SALE_YEAR_PIVOT = 40`), so upstream 27/28/29/31 became **2027–2031**, not 1927–1931 —
seven wlm sales with future dates.

Why that is not cosmetic: the comps query (`valuation/service.py:46`) bounds `sale_date` from **below
only** (`>= :since`, no upper bound), so a future-dated sale sits inside *every* lookback window and
surfaces as the freshest nearby comp. Three of the seven clear `DEFAULT_MIN_PRICE` (1000.0) and sit on
**vacant** parcels — the vacant-lot AVM that is the core product. A 1928 price ($2,500 / $5,000 /
$9,586) presented as a current comp.

Fixed by pivoting against a reference year (`date.today().year`, injected at the loader edge so the
resolver stays pure) instead of a constant. Chosen over simply lowering the constant to 26 because
that is correct today and silently wrong next year. Re-ingest verified: future-dated wlm sales
**7 → 0**; the three rows now read 1928. Four tests added, including one pinning the forward behavior.

**The unbounded upper bound in the comps query is still there** — this fix stops *wlm* from producing
future dates; it does not stop the query from trusting one. Any future loader with the same class of
bug lands the same way. Worth a follow-up.

## Two findings that change what earlier numbers meant

**1. The "44 of 56 sheriff rows skipped" figure was a reporting artifact, not a defect.** CivilView
`countyId=24` serves *all* of New Castle County; we load only Wilmington (`PIN LIKE '26%'`). The real
breakdown: **12 rows are Wilmington and all 12 reconciled — 100%**; 35 are other NCC towns, correctly
filtered by market scope; 9 carry no parcel id, of which only 3 are Wilmington and **all 3 are condo
units, not land**. `load_sheriff` derived its counter by subtraction, so a deliberate scope filter and
a genuine parse failure were indistinguishable — meaning a real reconciliation break would have hidden
inside a number that always looked alarming. Now counted and named separately. The
"address-match for OPA-less sheriff rows" follow-up carried since handoff-0028 is **lower priority
than it looked**: it would buy 3 condos.

**2. `docs/PRD.md` had never existed.** CLAUDE.md has cited it three times as the source of truth for
scope since the repo began; no commit ever touched that path. The spec only ever shipped as a 793KB
PDF under a different name (`962d8e6`: *"README links point at the PRD as currently shipped (PDF)"*).
Deleting the binary exposed a long-standing broken reference rather than creating one. The PRD is now
markdown at the cited path — 33KB, diffable — with the original wording preserved where it has been
overtaken (Elasticsearch in §5.1/§5.15/§14, superseded by ADR-0005) and the divergence recorded in a
provenance line rather than silently edited.

## Additional gotchas

- **A deploy does not apply a gate change.** `market_gate_item` rows are *seeded*, so the ops board
  keeps showing the old rows until `maintenance:seed_gates` runs.
- **A deploy does not fix stored data.** The pivot and date-bound fixes act at ingest/query time; prod
  rows already written stay wrong until re-ingested.
- **Distress recompute has a market-coverage tripwire that was global.** Scoping to one market would
  still have failed if *another* market lacked a profile; #37 narrowed it to markets in scope.
- **The job console renders `job.params` generically**, so a new param needs no frontend change.
