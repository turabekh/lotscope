### LR-B-003 — missing-data audit closed

All six findings fixed; `docs/launch-readiness/missing-data-audit.md` is now `Complete`.

Two of the three remaining findings **changed character once traced properly**, and both re-characterisations are recorded in the audit rather than edited away:

- **Finding 4 never leaked a false figure.** The `<= 0` guard caught the `or 0` immediately. The real defect was the inverse — a parcel whose zoning genuinely permits zero units was told the count *"could not be determined"*, reporting a known answer as missing data.
- **Finding 6 was not a §8.4 violation at all.** An unknown land value made the structure test trivially true, which *subtracts* from vacancy confidence. Missing data produced more doubt, never a false clearance. Its fix is behaviour-preserving by construction, with a test pinning the unknown and known paths to equal scores, so **no `recompute:vacancy` is required**.

Abatement was the one genuine gap: unreported exemptions read as "no abatement" and showed nothing. Now `bool | None` with a `not_evaluated` checklist item. **Its own test had asserted `has_active_exemption(None, None) is False`** — the bug encoded as expected behaviour, which is why it survived earlier review. Worth remembering as a review smell.

### LR-7B — buy-box matching and first-run guidance

`GET /underwriting/matches` resolves the caller's default profile buy box against `parcel_verdict`. The router prefix moved `/underwriting/profiles` → `/underwriting`; **every existing URL is preserved**.

§8.4 drove the design: a criterion the user states is never satisfied by a value we do not have. SQL three-valued logic enforces it (`NULL <= :ceiling` is never true) and the pure evaluator reports `not_evaluated` *with the reason*. Zero stays distinct from unknown — a 0% margin is evaluated and fails a 20% target; a missing margin is not evaluated.

`FirstSteps` tracks four actions from real state (watchlist, saved-search alerts, a profile that *actually carries* assumptions), with localStorage only for "opened a verdict", marked in the parcel store's `select()` so it counts however the dossier was reached.

### LR-9C/9D — support operations and policy surfaces

**LR-9D:** Terms, Privacy, Disclaimers, Disclosures, Refund, Corrections are a declared required set, admin-published, served at `/legal/:slug`. ## 3. Production state and the two incidents

### 3.1 The backup gate now works — and today it twice did not

**Morning:** a migration-bearing deploy was blocked by the backup gate because the VM's OAuth scope was `devstorage.read_only`. Unblocked with a one-off `skip_pre_migration_backup=true` (per-run input, deliberately not a repo variable). Migrations `a2f4c8d19b3e`, `b7e1d3f5c942`, `c4a8e2b6d071`, `d9f3b1c7e485` applied with no backup behind them.

**Then the backup turned out to exist.** A 407 MB dump stranded in `/tmp` from the failed attempt was a valid, complete `PGDMP` custom dump (54 tables) taken at **09:08:24Z**, seventeen minutes before migrations ran at **09:25:04Z**. It had only failed to *upload*. It is now preserved and verified byte-exact at:

```
gs://lotscope-501014-db-backups/lotscope-pre-migration-20260728T090649Z.dump
```

**Afternoon:** the scope was widened to `devstorage.read_write` and **verified by an actual write and delete from the VM**. The gate now works unattended. The next deploy will be the first to take a real pre-migration backup rather than skipping or rescuing one.

### 3.2 The IP incident — read before ever stopping the VM again

Widening OAuth scopes requires the instance to be `TERMINATED`. The VM had an **ephemeral** external IP. Stopping it released `35.231.170.181`; it returned as `34.148.129.129`. The old address could not be reclaimed (`Specified IP address is not allocated to the project`). DNS is at Namecheap, outside GCP, so the site was down on the domain until the owner edited two `A` records.

**Mitigation applied:** `34.148.129.129` is now a reserved static address (`lotscope-static`, `IN_USE`), so a future stop/start cannot repeat this.

**Lesson for the runbook:** check `natIP` allocation type *before* stopping a GCE instance, not after. Reserving the address first would have avoided the outage entirely.

Also note: after the restart, only `caddy` came back. The app-profile services need `docker compose --profile app up -d`. Bringing them up that way leaves `/health` reporting `"version":"unknown"` because the SHA build-arg is only set by `scripts/deploy.sh` — the code is unaffected and the next real deploy restores the stamp.

## 5. What is armed right now

Cron `9e35cab6`, hourly at `:23`. It reads the VM chain log and fires `gh workflow run deploy.yml --ref main` only when the full pass finishes cleanly, then verifies the result and deletes itself.

| Guard | Behaviour |
|---|---|
| Exit code | deploys only on `rc=0` |
| Stale log | ignores the pre-restart chain (`11:00:31Z`) so it cannot fire on the dead run |
| SHA pin | pinned to the tip at scheduling time; stops if `main` moved unexpectedly |

The stale-log guard already earned its place — the first watcher poll saw `full pass exited … rc=1` in the file and correctly declined to act. Without it, that poll would have deployed against a crashed run mid-recompute.

**Why cron and not a background process.** Two `deploy-when-done.sh` background watchers were killed within an hour each. Cron fires a prompt on an idle REPL rather than holding a long-lived process, so it is not exposed to the same kill. It is still **session-only** — nothing on disk, gone when the session ends.

A crash costs elapsed time, not data — chunks commit as they go. Restart it detached:

```bash

```

Deploying first is also defensible — the recompute can be re-run afterwards, and the four commits have been waiting a day. Verdicts computed before the deploy stay valid; `VERDICT_VERSION` is unchanged at `v8`.
