## 2. The fix, and what it moved

RTT delimits multi-party fields with `;` and the matcher split on whitespace, so `ASBELL WILLIAM;ASBELL DORA` produced the token `WILLIAM;ASBELL` and matched nothing. A debtor named on the sheriff's deed failed the grantor test and fell to `verify`/`medium`. **Defect fix inside ADR-0083's methodology — no version bump.**

Delimiter inventory checked before touching anything: of 5,133,119 grantor strings, **1,925,903 carry a semicolon**; ` AND ` (130,802), ` & ` (68,596), `/` (13,891) and `,` (5,238) are name-internal in every sampled case. Semicolon only. Debtor side: zero semicolons in 54,399 rows.

**Affected class, measured on production:** 299 of 54,401 delinquent phl parcels — **297 `medium` → `info`**, **2 the other way**, 202 vacant. `counts_toward_distress` unchanged on all 299, so distress did not move at all. 299 is **13.1% of the 2,282 sheriff-deed parcels**, well under the session's estimate.

**Recompute:** targeted, 299 of 299 in **58 seconds** — `recompute_verdicts` already accepts any sequence, so no sweep was needed. Risk fell on 296, rose on 3. Two risers are the named reversals; the third, `phl:062126700`, gained an `unsafe_structure` L&I designation from newer data — a targeted recompute re-evaluates every dimension, so unrelated movement is expected.

**Cache invalidation:** neither version string moves in this fix, so cached snapshots would have served the old text for seven days. Purged `summary:*:{parcel}:*` and `report:*:{parcel}:*` for exactly the 299 — 2 entries existed, since only viewed parcels are cached. Regeneration proven over HTTPS on `phl:362363700`.

**Residual, 2 parcels** — `phl:232331100` and `phl:221167100`, upstream duplicate-party-with-typos. The old matcher pooled tokens across different parties to reassemble a name present in none of them: lucky, not right. Both now read `verify`/`medium`, both rose 40 → 60, distress untouched. ## 8. Things that will bite

**A detached job on the VM needs `docker compose exec -d`.** `nohup … &` inside an `ssh` command does not survive the session closing — the first attempt ran RTT and died before the L&I loaders. `exec -d` detaches inside the container and survives.

**A concurrent duplicate ingest left the board reporting `failed` for a dataset that succeeded — fixed since, see below.** Two `li_violations` runs overlapped this session. The loser rolled back — its `ingest_run` row vanished, leaving an id gap — but `run_loader`'s `except` path calls `_record_failure`, which opens **its own session and commits independently**, by design, so a failure is recorded even when the main transaction rolls back. That `failed` status then outlived the rollback and overwrote the success written moments earlier. `dataset_freshness` read `violations | failed` while `ingest_run` read `success`, the data was complete, and `li_event` had zero duplicates.

It self-corrected when the second run finished and wrote `success`. But if a manual run ever overlapped the nightly, the board would report a healthy dataset as broken until the next successful run — the inverse of the failure PR #148 fixed, and the ops digest would alert on it. The parcel-facing freshness panel was never affected: it serves `as_of` and `data_vintage`, never `status`.

**Fixed, in two passes — the first was wrong, and the reason is worth keeping.**

`run_loader` stamps its start from the database clock and `record_freshness` declines a `failed` write when `last_success_at` is newer than that stamp, so a failing run can no longer overwrite a success that landed after it began.

The first pass wrote both timestamps with `func.now()`. **In Postgres `now()` is `transaction_timestamp()` — frozen at the transaction's first statement, not wall clock.** No loader commits mid-run (zero `.commit()` calls under `ingestion/loaders/`, only flushes), so an entire load runs in one transaction and `last_success_at` recorded when the winning run *started*, not when it finished — off by the whole load duration. The guard then failed in precisely the incident shape: nightly starts 22:00 and commits at 22:40 stamped `22:00`; the manual run starts 22:05, loses, fails at 22:50, and `22:00 < 22:05` let the clobber through. Only the ordering where the *loser* started first was ever protected, and the later-starting run is the likelier loser. `clock_timestamp()` fixes it.

That also corrects a pre-existing inaccuracy: `evaluate_freshness` computes `age = now - last_success_at`, so every dataset had been reporting itself one full run-duration staler than it was. `last_success_at` now means completion, which is what the column name always claimed. `runner.py` is the only writer of `dataset_freshness.status='failed'` and every success write also sets `last_success_at`, so the guard covers the whole surface. A failure the guard suppresses is still raised as `IngestionError` and logged as `ingestion_failed` — the operator who started the duplicate still sees it fail; only the shared board is spared. `IngestRun` is unchanged: the loser's row still rolls back with its transaction, so the id gap remains.

**A targeted recompute moves more than you changed.** It re-evaluates every dimension against current data, so parcels drift for unrelated reasons. Compare the flag you changed, not the score.

**`is_absentee` compares the property address against the mailing address on record** — whoever's record that is. On a parcel with stale OPA ownership it scores the previous owner's address.
