## 3. The fix that was wrong

`run_loader` records a failure in its own session, by design, so the loser of a concurrent duplicate ingest clobbered the winner's success and the ops board read red for a healthy dataset. #173 guarded the failure write on `last_success_at < run_started_at`.

**`func.now()` is `transaction_timestamp()`** — frozen at the transaction's first statement:

```
begin;
select now(), clock_timestamp();   -- 23:10:05.935833 | 23:10:05.941991
select pg_sleep(2);
select now(), clock_timestamp();   -- 23:10:05.935833 | 23:10:07.950034
```

**No loader commits mid-run** — zero `.commit()` calls under `ingestion/loaders/`, only flushes — so an entire load is one transaction and `last_success_at` recorded when the winner *started*. The guard then failed in exactly the incident shape: nightly begins 22:00 and commits at 22:40 stamped `22:00`; the manual run begins 22:05 and fails at 22:50; `22:00 < 22:05`; clobber proceeds. Only the ordering where the *loser* started first was ever protected — and the later starter is the likelier loser.

**The test was the real failure.** It recorded the competing success from a *freshly opened* session, whose transaction therefore began after the start stamp — the one shape in which the guard works. It went red without the fix and green with it and proved nothing. Production records success from the run's own long-lived transaction.

Same family as `CLAUDE.md` §12's "a test that builds its own staging row tests the row it built", but about **timing shape** rather than data shape. Before trusting a concurrency test, ask which transaction each timestamp comes from and whether that matches production's session lifecycle.

`clock_timestamp()` fixed it, and incidentally corrected a pre-existing inaccuracy: `evaluate_freshness` computes `age = now - last_success_at`, so every dataset had been reporting itself one full run-duration staler than it was.

## 4. Vacancy, measured

`VACANT_LAND_USES_BY_MARKET` registered `hbg` and `pgh` only, so Philadelphia never derived vacancy from OPA land use — 14,020 of 42,583 OPA-vacant parcels carried no flag, including 77% of `VACANT LAND - RESIDENTIAL`.

## 5. Public ownership, closed the same session (interim)

`is_city_owned` was set for `pgh` (8.7%), `hbg` (4.6%) and `wlm` (0.12%) and for **1 phl parcel of 588,606**, so every behaviour it gates — distress zeroing, the `public_ownership` risk flag, saved-search / watchlist / distress-list exclusions, assemblage candidacy — was inert in the flagship market.

**The authoritative source does not exist upstream** (§7). PR #181 therefore derives it from the OPA owner name, **explicitly interim**, per ADR-0085.

The pattern shape is load-bearing and was measured rather than guessed: `PHILADELPHIA HOUSING` must anchor or private `HLP PHILADELPHIA HOUSING` matches; `LAND BANK` must *not* anchor or the upstream misspelling `PHIADELPHIA LAND BANK` is missed; the `LLC` exclusion is what separates `PHILADELPHIA HOUSING AUTHORITY` from `PHILADELPHIA HOUSING GROUP LLC`, which anchoring alone cannot. Naive patterns matched 13,434; the rule matches **13,426**, excluding exactly the three private owners found by reading the owner strings first.

**Unlike vacancy this writes `false` as well as `true`,** because ownership has one truth rather than two complementary sources. Market scope is what makes that safe — the query *and* the UPDATE both pin `phl` — and it is the first thing to check if this is ever touched again.

## 6. The appeal guardrail, and what looking at the product caught

#178 stops the assessment surface producing an over-assessment or savings figure unless the subject is a vacant lot. The sweep's headline numbers were mostly artifacts — six of seven priced a rowhouse against vacant-land comps (0047 §5) — and we charge $79 for that packet.

Then the four changed surfaces were checked through the **authenticated production API**, with a throwaway account (registered, used, deleted; user count back to 11, zero dependent rows):

| surface | result |
|---|---|
| dossier · newly-vacant lot | `is_vacant: true`, **`Vacant lot — owner unlikely to occupy`** renders |
| distress · City-owned parcel | score **0**, tier `none` |
| vacant-only search | **`2138 N FAIRHILL ST` appears** — it could not before |
| leads | real factors returned, **zero public owners** |

**It found a defect nothing else did.** #178 checked comp sufficiency *before* vacancy, so a developed parcel got the not-vacant explanation only when the valuation engine happened to produce an estimate. With no estimate — common where there are no land comps nearby — the reader instead got *"Not enough assessment or comp data to evaluate the assessment."* Both messages are true and they say different things: the first states a deliberate product boundary, the second reads as a temporary gap and invites the reader to wait for a number that is never coming.

The withheld *figure* was correct in both orderings. Only the explanation was wrong, and the explanation was the entire point of #178. The suite passed either way, because no test exercised a developed parcel with no estimate. Fixed in #183: vacancy is a property of the subject, not of data availability, so it is checked first.

## 8. Things that will bite

**Do not deploy into a running nightly.** `deploy.sh` runs `docker compose stop api worker web` unconditionally and has no idea what it is killing. A deploy whose containers came back at 04:04:04 coincided with the 04:00 nightly stopping dead at 04:00:49, where the previous night ran through 04:03:24; `dc_parcels` failed on a connection error and `tcrp_zoning_districts` recorded *"Cancelled before completion"*. Causality is likely but not proven — `dc_deed_references` succeeded at 04:00:42, between the two failures, which a clean worker-stop would not explain. Both were re-run and are green. **Check for running jobs before deploying, and check the ops board after.** Neither happened; the failures sat unnoticed for seven hours and would have alerted the digest on a healthy system — the same class of bug §3 fixed.

**A hung `docker-credential-desktop` turns every integration test into a green-looking SKIP.** `docker build` and `pull` hang at manifest resolution while container networking is fine, and testcontainers reports `docker is not available` as a **skip** with the run still exiting 0. The unit suite took **2565s**; after removing `"credsStore": "desktop"` from `~/.docker/config.json` (backed up to `config.json.bak-20260824-062348`) the *full* suite ran **1860 passed, 0 skipped, in ~100s**. **Check `0 skipped`, not just `passed`** — the integration layer can vanish without turning anything red.

**`make docker-prune` removes `lotscope/postgres:test`,** so the next integration run skips until `make test-image` rebuilds it. It looked like a code failure first.

**A deploy needs `tmux` on the VM,** not `nohup` — 0047 §8 still applies; `tmux new-session -d` survives the SSH session closing.

**`recompute-distress` sweeps every market,** not just the one you changed. The first sweep ran without a baseline for the other three, so their values could be stated but not proven unchanged; the second returned **hbg 3, pgh 8,654, wlm 0** — identical. Two sweeps agreeing settles it after the fact without excusing the omission. Baseline before the next one.

**A targeted verdict recompute is mandatory for a within-version data correction.** Lazy recompute fires only on version mismatch, so stored rows would otherwise stay stamped `v11` while disagreeing with the engine indefinitely. Same for the AI caches — `CLAUDE.md` §12.
