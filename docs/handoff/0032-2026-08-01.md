### 2.1 The deploy path had been dead for three days

The first deploy failed on `dial tcp ***:22: i/o timeout`. The cause was the second-order half of the 2026-07-28 IP incident: DNS was corrected at Namecheap, but **`deploy.yml` connects to a literal IP held in the `VM_HOST` secret**, last set 2026-07-06. The site looked healthy the whole time because the site does not use that secret — only a deploy does.

`VM_HOST` now holds the reserved static `34.148.129.129`. **After any future IP change, update the secret in the same breath as DNS**, and when a deploy times out on port 22, check `gh secret list` timestamps before suspecting the firewall (`default-allow-ssh` is `0.0.0.0/0`).

### 2.3 Backups are scheduled and a restore has been performed

`LR-B-033` was mostly built already; two things were genuinely missing.

**No schedule existed.** Backups ran only before migrations, which are rare — so real exposure between schema changes was weeks, while the runbook advertised a 24-hour RPO on the strength of "whatever schedule is configured." Nothing was. A **weekly cron** now runs Sundays 03:00 UTC, and the **RPO is restated as 7 days** to match what the configuration supports. Nightly is a few cents a month if that trade looks wrong later.

`PATH` is set explicitly in the crontab because `gcloud` lives in `/snap/bin`, which cron's default `PATH` excludes — without it the job fails weekly with `command not found` and nothing announces it.

**No restore had ever been performed.** One now has: `pg_restore` rc=0, zero stderr, 4s download + 4m19s restore, every count identical to live. The only difference was `policy_document` absent and `alembic_version` at `d9f3b1c7e485` — correct, because the dump is labelled `pre-migration`. Recorded in `gates.md` G6; **next test due 2026-09-01**.

A keyword search presented as a measurement. Corrected in §1.3 of the review rather than edited away, because the pattern is more useful than the tidy version.

**Check the call path to a user, not to the next layer.** LR-B-004 is the fourth instance: `field_trust` shipped without persistence, LR-6A/6C/6D were unreachable until 6E, LR-9C built endpoints for orphaned services and stopped before the UI. Verification for LR-B-004 was therefore done against the running API through a real admin browser session, not against the component mount.

**Two environment traps in the e2e suite**, both of which cost a CI round:

- **CI has no Anthropic key.** An assertion on the AI `SnapshotPanel` passes locally and fails there. CI also lacks the real overlay and RCO geometry a developer's local database holds. Assert on verdict-derived output, never the AI narrative or incidental local data.
- **The onboarding tour blocks everything for a new user.** Every flow registers a fresh account, so the dialog mounts and its backdrop intercepts clicks. Dismissing it requires *waiting for it to appear* — an instantaneous visibility check races the mount and silently skips.
